## Frozen method contract

- π0 is frozen before data collection. Nominal motion, language/task execution, and low-level controller law are unchanged across methods.
- Physical adaptation is setpoint-only: the method may select a force setpoint, but may not alter the nominal trajectory, feedback law, grasp pose, object geometry, or reset semantics.
- The physical state is (z=(\text{friction},\text{mass})). The rejected old “Joint” neural architecture is not the joint-physics method.
- The runtime quantity is \(\bar p(F\mid D_q,x)=\mathbb E_{z\sim b_\phi(z\mid D_q)}[p_D(y_{task}=1\mid x,z,F)]\).
- The primary selector is \(F^*=\min_{F\in S_F}\{F:\bar p(F\mid D_q,x)\ge \rho_{sel}\}\). If no candidate passes, use the pre-registered maximum-safe fallback and report its rate.
- `rho_sel` is selected using TRAIN/DEV calibration and frozen before locked TEST. `rho_env` is a separate, pre-registered evaluation-only threshold (default 0.50 unless the DEV protocol freezes another value) used to construct the empirical simulator reliability frontier. `rho_env` is never exposed to the runtime selector.
- Every locked-test rollout starts from a fresh reset and runs to the end of the task. No test outcome, empirical test frontier, or test failure label changes a selector, threshold, checkpoint, candidate set, or task choice.

## Evaluation rules

1. Primary comparisons are paired by task, physical root, friction/mass cell, initial state, and repeat. Report cluster-bootstrap 95% CIs with physical root as the cluster.
2. `under-force` means selecting below the empirical `rho_env` frontier or failing to cross the runtime `rho_sel` threshold when a valid frontier exists. `excess-force` is selected force above the empirical frontier, reported separately from fallback.
3. A test-time empirical frontier is an evaluation label only. It cannot be queried by a selector, calibration routine, planner, or re-query gate.
4. The task is frozen using π0-independent screening criteria: reachability, nonzero low/high force contrast, and for long horizon a model-independent delayed-failure regime in which lift succeeds but transport/turning/placement/close later fails.
5. If a DEV gate fails, diagnose and repair on TRAIN/DEV, rerun the gate, and record the change. A failed gate is not permission to silently drop E6 or E7. If a repaired DEV hypothesis remains false, mark the hypothesis `COMPLETE_NEGATIVE` and remove only the unsupported paper claim.

## Explicit mass closure gates

- **M1 — mass query identifiability:** establish that the query contains mass information on held-out roots.
- **M2 — mass-sensitive task qualification:** freeze a task only after a tested low-force failure and a tested reliable high-force success, with π0-independent screening.
- **M3 — mass physical identification:** compare Vision, Physical, Vision+Physical, SysID, and GT, including mass MAE, band/rank accuracy, calibration, and cross-confusion.
- **M4 — mass full-task force adaptation:** compare mass-aware, friction-only, and nominal policies under the same Direct and controller semantics.
- **M5 — mass fresh E2E:** run fresh reset-to-end locked TEST rollouts and report SR, force, under-force, excess-force, fallback, latency, and failure stage.
